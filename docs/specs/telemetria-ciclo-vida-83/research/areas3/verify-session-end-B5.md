# Verdict: needs_changes

## Issues
- [major] §3.3 step 7 and §3.6: a streaming jornada segment should skip finalize_segment_native/close_scheduled and rely solely on the IndexedDB WAL through autoRecoverAll at next boot.
  - Evidence: The repo documents the opposite source of truth. scheduled_recording/service.rs:767-772 says: "el buffer de React no es durable para una sesión de 8h ... con la ventana al tray el guardado legacy dependía de un webview oculto/throttled". service.rs:1122 says: "Fuente de verdad = `transcripts.json` en disco". The spec does write transcripts.json at session end, but nothing reads it at next boot for streaming: useTranscriptRecovery.ts:199-262 rebuilds the meeting only from IndexedDB. Any transcripts the hidden or throttled webview never persisted are lost, which is worse than today's graceful path. It also bypasses MIN_SEGMENT_WORDS, which the spec only lists as an open question, and that revives discarded segments (#4 del piloto).
  - Fix: Keep finalize out of WM_ENDSESSION, but leave durable state that Rust can finish at next boot. At session end, write a small marker with std::fs, e.g. `<folder>/.session_end_pending.json` = {meeting_name, owned_since, trigger:"jornada"|"manual", enforce_min_words}. At next boot a Rust pass (next to the batch planner's orphan pass) does three things: recover_audio_from_checkpoints, then finalize_segment_native(enforce_min_words per trigger), then records the outcome in the marker. autoRecoverAll must skip or delete IndexedDB records whose folderPath has a resolved marker (dedup by an on-disk marker, not by the SCHEDULED_JORNADA_CLOSED event). Manual streaming can keep the IndexedDB path, or use the same marker with enforce_min_words=false.
- [major] Commit (iii): retrying once without the LAST checkpoint and returning 'partial' makes recovery tolerate a truncated chunk; 'Keep the dropped file on disk'.
  - Evidence: (a) recoverMeeting calls cleanup_checkpoints unconditionally after saveMeeting, even when audioRecoveryStatus is 'failed' (useTranscriptRecovery.ts:270-278). So in streaming the "kept" chunk and every good chunk are deleted right after a failed or partial merge. (b) The bad file isn't always the last one. If the early checkpoint started at QES fails, its errors are counted before `errs0` is read (errs0 is read after acquire_encode_slot, incremental_saver.rs:202-205 increments on any non-zero exit). The final encode then succeeds, so the truncated file is second-to-last. The concat fails, the retry without the last file fails again, and the whole recording's audio is lost. (c) recover_audio_from_checkpoints sorts by filename (incremental_saver.rs:554), so 'last' means highest name.
  - Fix: In recovery, when the concat fails, validate each .mp4 on its own (`ffmpeg -v error -i f -f null -` or ffprobe) and concat only the valid ones. Return 'partial' with the excluded names, and move excluded files to a quarantine name instead of deleting them. In useTranscriptRecovery.ts, call cleanup_checkpoints only when status === 'success', or 'partial' with nothing excluded. In flush_for_session_end, read the error counter at QES time as well, so a failed early chunk is renamed (e.g. `.failed`) rather than left in the concat set.
- [major] The final encode at ES finishes within HARD_BUDGET once dispatched, and a failed encode's file should be deleted (§3.3, risks: 'A failed encode's file is deleted').
  - Evidence: The checkpoint encoder is a separate console child process: encode.rs:101-114 uses std::process::Command with CREATE_NO_WINDOW and pipes stdin. Windows handles it on its own during logoff or shutdown. Microsoft (ms700677): "Windows Vista will also not allow console applications ... to block shutdown ... takes over 5 seconds ... Windows will automatically terminate it". So the ffmpeg child can be killed, or signalled and exit non-zero, while Maity is still inside its ES budget. encode_single_audio returns Err on any non-success status (encode.rs:158-165), which increments encode_errors (incremental_saver.rs:202-205). That also happens for a SIGTERM-style stop that leaves a valid but shorter mp4, and the spec would then delete real audio. The spec lists child survival only as UNVERIFIED and has no mitigation.
  - Fix: In setup(), call SetProcessShutdownParameters(0x3FF or similar >0x280, 0) on Windows. It is already available via Win32_System_Threading (windows-0.58 System/Threading/mod.rs:1973). The system asks higher-level processes first, so Maity's QES/ES happen while its ffmpeg children (default 0x280) are still alive. Serialization across levels during ES is UNVERIFIED, so E2E must check it. Never delete a failed chunk inside the ES path; rename it and let recovery-time validation decide.
- [minor] 'Nothing in the fast path needs the main thread' / 'every step is under timeout_at' bounds the session-end exit.
  - Evidence: tokio timeouts only fire at await points. The fast path contains synchronous blocking calls polled on the main thread inside block_on: RECORDING_MANAGER is a std Mutex (recording_lifecycle.rs:548); stream_manager.stop_streams() is sync (recording_manager.rs:280) and drops the cpal WASAPI stream (stream.rs:320-332), which joins its audio thread. A stall there overruns HARD_BUDGET, and timeout_at can't stop it.
  - Fix: Run the flush on a runtime worker and bound it from the main thread: `block_on(async { let h = tauri::async_runtime::spawn(flush_recording_for_session_end(t0)); let _ = tokio::time::timeout_at(t0 + HARD_BUDGET, h).await; })`. This bounds the main thread even if a sync call inside blocks. Do the same for DB cleanup and the sidecar kill.
- [minor] Taking the manager out of RECORDING_MANAGER at ES always finds it, and request_early_checkpoint can always clone the saver handle from it.
  - Evidence: switch_audio_device temporarily take()s the manager out of the mutex across an await (recording_commands.rs:241-256). Auto-reconnect reuses it on DeviceReconnected. Endpoints (Bluetooth, USB, remote-session audio) commonly vanish during logoff, so this window can overlap session end. The early checkpoint and the ES flush then see None and skip the tail flush.
  - Fix: When recording starts, store a clone of the IncrementalAudioSaver Arc (and the folder) in a session-end static, and clear it on stop. Use it as a fallback when RECORDING_MANAGER is None, both at QES and at ES.
- [minor] The block reason and flush trigger only when phase is Recording|Paused (is_session_active / is_recording()).
  - Evidence: recording_phase.rs:61-63 excludes Starting and Stopping. During a jornada rotation or close, the finalize runs for up to 300 s in phase Stopping (planner.rs:161-163 comment, service.rs close_scheduled). A session end then gets no ShutdownBlockReason, so with no visible window it is killed at 5 s. The in-flight merge and finalize_segment_native are also cut mid-write while DB cleanup closes the pool after 1 s.
  - Fix: Register the reason whenever phase != Idle. In the Exit branch, log `phase=Stopping (rotation/stop en curso)` and rely on checkpoints plus the marker/orphan recovery, since `.checkpoints` are deleted only after a successful merge (incremental_saver.rs:321-328). Document this edge case in REGLAS.
- [minor] SessionEndCell::record_if_absent at ES(TRUE) 'does not overwrite a QES record', with a 120 s TTL on fresh().
  - Evidence: If a present-but-stale QES record exists (older than the TTL), record_if_absent keeps it and fresh() returns None. The exit is then classified Unknown via SM_SHUTTINGDOWN even though ES carried an exact lParam.
  - Fix: record_if_absent should also replace a record older than RECORD_TTL. Add a table test for it.
- [minor] The manual-verification log lines ('[session_end] flush: …', 'cleanup complete (session end, N ms)') are the evidence of success.
  - Evidence: The process is terminated right after ES returns, so buffered log output may never reach the rotating file. The spec also drops the recording.stopped telemetry that the normal stop emits from Rust (recording_lifecycle.rs:514-534), and the live_feedback::stop coach summary.
  - Fix: Call log::logger().flush() before returning from the session-end branch. Emit recording.stopped (the SQLite outbox is async, no main thread needed) inside the budget before DB cleanup, or carry it in T2's app.exit payload; state which one.
- [minor] Evidence: docs/REGLAS_AUDIO_GRABACION.md 'Pendiente conocido ... posible duplicado del que Rust ya guardó' supports the session-end duplicate risk.
  - Evidence: REGLAS_AUDIO_GRABACION.md:76 is about the markMeetingAsSaved race during jornada rotation (sessionStorage overwritten by the new segment), not about session end or a blocked main thread.
  - Fix: Cite it as an analogous known duplicate path, and keep the session-end duplicate marked as inferred and not reproduced.

## Corrected design notes
The core of the spec is right. Keep the subclass on the main HWND for QES/ES kind detection, never veto, register ShutdownBlockReasonCreate at QES and release it on ES(FALSE), take a short-budget branch in RunEvent::Exit only when a session end is observed, and never merge, emit or call window getters inside ES. Change these parts:

1) Streaming recovery source of truth. Don't rely only on IndexedDB. At session end, after writing transcripts.json, write `<folder>/.session_end_pending.json` synchronously with std::fs: {meeting_name, owned_since/started_at, trigger: jornada|manual, enforce_min_words, process_id}. At next boot a Rust pass beside planner::recover_orphans (streaming rows only; batch keeps its queue) does: recover_audio_from_checkpoints → finalize_segment_native(enforce_min_words = trigger==jornada) → mark the marker as resolved (Saved/Discarded). autoRecoverAll then skips or deletes IndexedDB records whose folderPath carries a resolved marker. This removes the duplicate risk without webview events, keeps MIN_SEGMENT_WORDS, and survives a throttled or suspended webview.

2) Bound the main thread for real. Use `block_on(async { let h = spawn(flush_recording_for_session_end(t0)); let _ = timeout_at(t0+HARD, h).await; let _ = timeout(DB_BUDGET, spawn(db_cleanup)).await; let _ = timeout(SIDECAR_BUDGET, spawn(sidecar_kill)).await; })`, so sync-blocking calls (cpal drop and join, std Mutex) can't stretch the ES handler. Call log::logger().flush() before returning.

3) Keep ffmpeg children alive. Call SetProcessShutdownParameters(0x3FF or any level >0x280, 0) once in setup() (Win32_System_Threading is already enabled). Maity then gets QES/ES before its default-level ffmpeg and llama-helper children. Verify in E2E, because cross-level serialization during ES is UNVERIFIED.

4) Never delete audio in the ES path. When the final or early encode fails, rename the chunk to `.failed`. Read the error counter at QES time as well as at the final dispatch.

5) Commit (iii) becomes per-file validation. When the concat fails, probe each chunk (`ffmpeg -v error -i f -f null -`), concat only the valid ones, return 'partial' plus the excluded names, and quarantine the rest. In useTranscriptRecovery.ts, gate cleanup_checkpoints on status==='success' (or partial with nothing excluded). Today it wipes .checkpoints even after a 'failed' merge (useTranscriptRecovery.ts:270-278).

6) Keep a session-end static with the saver Arc and folder, set at recording start and cleared at stop, as a fallback when switch_audio_device has taken the manager out of RECORDING_MANAGER.

7) Register the block reason whenever phase != Idle, including a rotation or close finalize in Stopping, and log that case. record_if_absent should replace records older than the TTL.

8) Say where recording.stopped goes at session end: emit it via the outbox inside the budget, or add it to T2's app.exit payload.

Budgets (1.5/2.5/7 s + 1 s + 0.5 s), the Unknown/SM_SHUTTINGDOWN fallback, the exit_reason strings, the Guardian backup branch and writing commit bodies with `git commit -F` all stay as specified.
